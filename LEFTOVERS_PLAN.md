## L1. Приставной носик (kind: 'applied')

### L1.1 Состояние — `src/geo/spout.ts`

Расширить `SpoutState`, старые поля остаются как есть (это параметры lip):

```ts
export interface SpoutState {
  on: boolean;
  /** 'lip' — оттянутый край (как сейчас); 'applied' — приставная трубка */
  kind: 'lip' | 'applied';
  // --- lip ---
  pullMm: number; widthDeg: number; zone: number;
  // --- applied ---
  /** высота крепления оси носика к стенке, доля высоты */
  attachAt: number;      // 0.2…0.85, дефолт 0.45
  /** горизонтальный вынос кончика от стенки, мм */
  lengthMm: number;      // 15…150, дефолт 70
  /** высота кончика, доля высоты изделия; >1 — выше венчика */
  tipAt: number;         // 0.5…1.3, дефолт 1.0
  /** наружный диаметр у основания, мм */
  baseMm: number;        // 12…80, дефолт 34
  /** наружный диаметр у кончика, мм */
  tipMm: number;         // 6…40, дефолт 16
  /** наклон кончика к горизонтали, градусы */
  tipAngleDeg: number;   // 20…85, дефолт 55
}
```

`sanitizeSpout`: `kind` из строки, **дефолт `'lip'`** — старые ссылки и
пресеты не меняют смысла. Дополнительно `tipMm ≤ baseMm` и
`tipAt ≥ attachAt + 0.1` (носик не смотрит вниз — из него бы выливалось).
Санатор по-прежнему не бросает и идемпотентен — `state.test.ts` это
проверит сам.

`makeSpout` (вытяг края) при `kind === 'applied'` возвращает `() => 0` —
две механики не складываются.

### L1.2 Геометрия — там же, через `sweep.ts`

Машинерия готова: `sweepTube` умеет переменное сечение (section(t)),
кривая — `bezier`/`bezierTangent`, всё в плоскости разъёма y = 0, x > 0
(инвариант: ручка при x < 0, носик при x > 0).

```ts
/** Наружная трубка носика; null, если выключен или kind !== 'applied'. */
export function buildAppliedSpout(state, profile: ProfileDef, heightMm): SurfaceMesh | null
/** Внутренний канал под вычитание; стенку канала диктует вызывающий. */
export function appliedSpoutChannel(state, profile, heightMm, wallMm): SurfaceMesh | null
```

Кривая (по образцу ручки, но проще — без solvePush, точность выноса тут
не обещана ползунком «в мм от стенки», длина меряется до кончика):

- `p0 = (r(attachAt) − embed, 0, attachAt·H)`, embed как у ручки
  (`min(2.5, r·0.4)`); касательная в p0 — горизонталь `+x` (стык под 90°,
  тот же довод, что у ручки).
- `p1 = (r(attachAt) + lengthMm, 0, tipAt·H)`; касательная в p1 —
  `(cos tipAngleDeg, 0, sin tipAngleDeg)`.
- Контрольные точки: `c0 = p0 + d·(1,0,0)`, `c1 = p1 − d·(cos a,0,sin a)`,
  `d = 0.35·|p1 − p0|`. Даёт классическую чайниковую дугу; если на глаз
  (через `snap.mjs`) окажется вялой — крутить 0.35, это единственная
  свободная константа.
- Сечение круглое: `halfDepth = halfWidth = lerp(baseMm/2, tipMm/2, t)`.
- SEGMENTS/RING — как у ручки (64/24).

Канал: та же кривая и тот же линейный конус радиусов, но
`r_канала(t) = r_наружн(t) − wallMm`, clamp снизу 1.2 мм (тоньше канал
не нужен и вырождается). Концы продлить за пределы [0,1] (Безье честно
экстраполируется, отдельной геометрии не надо):

- за основание — настолько, чтобы гарантированно пробить полость:
  сдвинуть p0 канала внутрь до `x = r(attachAt) − wallMm_сосуда − embed − 3`;
- за кончик — на +4 мм вдоль касательной: вычитание вскрывает торец
  трубки, устье получается открытым.

Плоские веерные торцы канала — норм: он существует только как вычитаемое.

### L1.3 Сборка — `src/geo/assemble.ts`

- `buildSolidVessel(csg, p, handle, spout)`: к телу и ручкам добавляется
  **сплошная** наружная трубка (`buildAppliedSpout`) через тот же
  `unionAll`. Канал тут не вычитается: мастер и оснастка работают со
  сплошным позитивом — в шликерном литье носик и так отливается полым,
  проход прорезают по сырому.
- `buildPrintableVessel(...)`: было `(shell ∪ handles) − cavity`, станет

  ```
  (shell ∪ handles ∪ spoutOuter) − cavity − channel
  ```

  (`cavity` и `channel` можно вычесть одним `subtract` от их union).
  `wallMm` для канала — `hollow.wallMm`: стенка носика равна стенке тела,
  отдельный ползунок не нужен. Вместимость по-прежнему считается от
  полости тела — вклад канала мал, не усложняем.

Сигнатуры меняются — поправить обоих вызывающих (`main.ts`,
`tests/vessel.test.ts` и т.п. по компилятору).

### L1.4 Анализатор — `src/geo/mold/analyze.ts`

`AnalyzeOptions` + `hasSpout: boolean` (только applied!). Действует как
`hasHandle`: одночастная форма исключена, в `reason` свой текст:
«Приставной носик торчит вбок — вверх изделие не вынуть, нужен разъём
вдоль оси». Носик лежит в плоскости разъёма → половины снимаются, ничего
больше в анализаторе трогать не надо. Сквозного отверстия носик, в
отличие от ручки, не делает, но на выбор схемы это не влияет.

В `main.ts` флаг считается как `state.spout.on && state.spout.kind === 'applied'`
(превью-`outer` трубку не содержит, числом анализатор её не увидит —
потому и флаг, ровно как с ручкой).

Блок/ванночка (`block.ts`, `bath.ts`) габарит берут из солида — носик
попадает туда сам, правок не жду; проверить тестом (L1.8).

### L1.5 Превью — `src/main.ts`

Как ручка: в режиме vessel носик рисуется отдельным мешем без CSG —
`scene.setMeshes([hollow.mesh, ...handles, ...(spoutTube ? [spoutTube] : [])])`.

видно — и не надо, честная геометрия уходит в STL (тот же компромисс,

`tipAt < 0.92` — «Кончик носика ниже венчика: наполнить изделие выше

## L2. Весь CSG в воркер + живой прогресс

Цель: главный поток вообще не грузит manifold-3d (~2 МБ WASM) и никогда
не замирает; `#progressWrap` из index.html оживает.

### L2.1 Протокол — `src/worker/protocol.ts`

Чистые типы, без DOM и без Three:

```ts
export type CsgJob =
  | { kind: 'mold-preview'; state: AppState; segments: number }   // exportMode из state
  | { kind: 'export'; state: AppState };                          // segments = state.resolution

export interface JobPart {
  id: string; label: string;
  positions: Float32Array; indices: Uint32Array; normals: Float32Array;
  /** блокирующие проблемы экспорта; для превью пусто */
  blocking: string[];
}

export type WorkerOut =
  | { type: 'progress'; jobId: number; step: number; total: number; label: string }
  | { type: 'done'; jobId: number; parts: JobPart[] }
  | { type: 'error'; jobId: number; message: string };
```

Прогресс покрупному, по этапам: manifold внутри одной операции прогресса
не отдаёт, и притворяться не будем. Этапы: «сборка изделия» → «анализ
разъёма» → «деталь i из n» → «проверка меша». Для vessel-экспорта этапов
меньше, но их тоже 3–4 — бар живёт.

### L2.2 Воркер — `src/worker/csg.worker.ts`

Module worker. Внутри: `initCSG()` (модульный синглтон уже рассчитан на
«раз на процесс/воркер»), `sanitizeState` на входе (инвариант «всё
внешнее проходит санацию» — граница воркера тоже граница), дальше ровно
те же вызовы, что сейчас в `main.ts`:

- mold-preview → `toBuildParams` → `buildSolidVessel` → `analyzeMold` →
  `buildMaster` / `buildBaths`;
- export vessel → `buildPrintableVessel` + `validateMesh`/`assessExport`
  (валидация на 384 сама по себе сотни мс — ей тоже место здесь);
- export master/bath → как превью, но на `state.resolution` + валидация.

Ответ — с transfer list по всем буферам (позиции/индексы/нормали),
копий не делать.

`buildMoldParts` из `main.ts` переезжает сюда целиком.

### L2.3 Клиент — `src/worker/client.ts`

```ts
export class CsgClient {
  run(job: CsgJob, onProgress?: (p) => void): Promise<JobPart[]>;
}
```

- Один воркер, ленивое создание:
  `new Worker(new URL('./csg.worker.ts', import.meta.url), { type: 'module' })`.
- Однозадачный: воркер жуёт одну задачу, очередь глубиной 1, новая
  mold-preview-задача **вытесняет** ожидающую (не бегущую — WASM посреди
  операции не прервать). Вытесненная резолвится отказом, который клиент
  глотает. Это замена нынешнему паттерну `stamp !== generation`; сам
  stamp-контроль в `main.ts` остаётся как второй рубеж.
- Экспорт в очереди не вытесняется (кнопка и так задизейблена на время).

### L2.4 `main.ts`

- Убрать `initCSG`, `buildSolidVessel`, `buildPrintableVessel`,
  `buildMoldParts`, импорт `csg.ts` — main больше не знает про WASM.
- `showMold(stamp)` → `client.run({kind:'mold-preview',…})`, прогресс — в
  `auditEl` текстом («деталь 1 из 3…»), результат как сейчас в

- `runExport` → `client.run({kind:'export',…}, onProgress)`; blocking
  приходит из воркера готовым. `encodeSTL` и `download` остаются в main —
  они копеечные.
- Прогресс-бар: helper `progress(step, total, label)` / `progressDone()`,
  дергающий `#progressWrap/#progressFill/#progressLabel` (разметка и CSS
  уже есть). Показывать на время экспорта; на превью оснастки достаточно
  текста в `auditEl`, бар на полсекунды только мельтешит.

`analyzeMold` для подписи схемы разъёма (лёгкий, по превью-мешу) остаётся
в main как есть — он без CSG.

### L2.5 Риски и проверка

- **Главный риск**: загрузка `manifold-3d` WASM внутри vite-воркера — и в
  dev, и в прод-сборке (`worker.format` в vite 5 для module worker может
  потребовать явного `worker: { format: 'es' }` в конфиге; wasm-ассет
  должен попасть в бандл воркера). Первым делом в L2 — спайк: пустой
  воркер, `initCSG()`, `Manifold.cube`, обе сборки. Если dev-режим
  упрётся — известный обход: `?url`-импорт wasm и `locateFile` у Module.
- `npm run smoke` и `npm run smoke -- --preview` — обязательны оба:
  бандлинг воркера в dev и prod различается, а смоук уже гоняет реальный
  экспорт STL, т.е. проверит воркер от и до.
- Vitest воркер не гоняет — и не надо: вся логика в чистых `geo/`-функциях
  и уже покрыта; воркер и клиент — тонкая обвязка, её проверяет смоук.
  `protocol.ts` держать без исполняемого кода, чтобы нечего было тестить.
- Память WASM: `CsgScope` уже дисциплинирует; воркер живёт долго — после
  экспорта на 384 куча вернётся, следить не нужно.
